## Likely questions

- **Why not partition the fact?** 24k rows: partitions would be tiny files. Liquid clustering on `date_key` gives data skipping without the small-file problem and can be changed later without rewriting the table.
- **Why `GENERATED BY DEFAULT` and not `ALWAYS`?** `ALWAYS` forbids explicit values, so the −1 unknown member could not be inserted.
- **What happens if a new product appears tomorrow?** Its lines first land on −1 (no sale lost). After the product reaches the catalogue, the next run's `MERGE` updates those fact rows to the real key (the record hash changes).
- **What if the extract becomes incremental?** Drop `WHEN NOT MATCHED BY SOURCE THEN DELETE` from the fact MERGE, keep the rest; bronze would switch to `COPY INTO` / Auto Loader to ingest only new files.
- **Why is `unit_cost` on the fact?** `dim_product` is SCD1; storing cost at load time keeps historical margin stable if the cost changes.
